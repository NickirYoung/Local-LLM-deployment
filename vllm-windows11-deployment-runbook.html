01 / Read this firstCapable hardware. Validate the whole system.

This server has substantial local-inference capacity. Its practical limits will come from memory per GPU, communication between cards, cooling, software compatibility, and workload shape. The CPUs and system RAM are ample; adding them together with GPU memory does not create one fast shared memory pool.

Recommended starting path

Windows 11 → WSL2 → Ubuntu 24.04 → isolated Python environment → vLLM. Begin with a one-GPU test, validate communication, then compare model layouts. For an unattended 24/7 service, native Linux remains the preferred operational target if the owner can choose the host OS.

Known from the owner

Windows 11 is the intended operating system. The hardware specification above is reported, not independently inventoried.

Still to discover

Windows edition/build, motherboard/chassis, storage, driver, actual GPU topology, business tasks, document permissions, target concurrency, and recovery requirements.

Until those workload targets are agreed and tested, call the result a pilot. This document contains implementation examples and engineering estimates; no benchmark or hardware test has been run on the friend's server.

OWNER / DEPLOYMENT AGENT
Use this attached HTML runbook as the deployment specification for my local business LLM server. Read all sections, including troubleshooting and acceptance, before making changes.

Objective
Get a reproducible vLLM pilot running on my existing Windows 11 server, validate all available GPUs, compare sensible model layouts, and leave working startup, recovery, security boundaries, and deployment evidence. Continue through the authorized setup and testing; report precise external blockers instead of stopping at a plan.

Reported hardware (verify, do not assume detected)

- 2 x AMD EPYC 9684X, 96 cores / 192 threads each
- 24 x 64 GB DDR5-4800 system RAM
- 8 x NVIDIA GeForce RTX 4090, 24 GB each
- Windows 11; exact edition/build, motherboard, GPU topology, storage, and business workload are unknown

Execution approach

1. Start with read-only inventory. Record Windows edition/build, BIOS, CPU/core/thread counts, usable RAM, storage, NVIDIA driver, WSL version/distributions, GPUs, occupied ports, and existing workloads. Do not expose secrets in logs.
2. Verify the live upstream requirements for vLLM, Python, CUDA/driver compatibility, WSL, and the selected model. Use official sources linked in this document. Select a stable compatible release, record exact versions, and use its matching documentation. Do not silently adopt nightly builds or an unofficial Windows fork.
3. Use Ubuntu 24.04 in WSL2 as the initial Windows route. Reuse a suitable existing distribution or create a dedicated one. Preserve Windows, existing files, and unrelated services. Back up and merge configuration changes; do not overwrite .wslconfig or wsl.conf wholesale. Check active WSL work before restarting it.
4. Install the NVIDIA driver on Windows; do not install a Linux display driver inside WSL. Use a clean Python environment and Linux-native paths on adequately sized NVMe storage.
5. Validate GPU computation individually, then multi-GPU communication progressively. Start with one GPU and Qwen3-8B, then test groups of 2, 4, and 8 where available. Separate hardware/driver failures from model-memory failures.
6. Establish a pinned Qwen3.8-27B BF16 text-only baseline on four GPUs if the current stable release supports it. Compare PP4/TP1 with TP4/PP1. Trial two independent four-GPU instances if resources permit. Use a compatible, verified smaller model while resolving newer-model support rather than changing the host OS.
7. Evaluate the documented INT4 candidate in a separate configuration, starting with one or two GPUs and conservative limits. Preserve the BF16 baseline. Compare business quality, latency, memory, and concurrency. Do not assume the largest model is best.
8. Keep inference endpoints bound to loopback during the pilot. Prepare the business access layer with HTTPS, identity, per-user limits, endpoint allowlisting, and audit policy. Reuse existing approved infrastructure when possible. Keep a completed local pilot available while missing identity/domain/certificate choices are resolved. Do not expose raw vLLM publicly.
9. Configure systemd and Windows startup under the actual WSL-owning Windows account. Test readiness after a cold reboot with no interactive login, session closure, worker failure, and restart. Coordinate disruptive reboots with the owner and active work.
10. Test the actual business workload and document a concurrency/context/output envelope. Use synthetic benchmarks only as capacity probes. If the workload is still unknown, label the result a provisional pilot and list the missing acceptance targets.
11. Record model repository plus commit, software versions, launch configuration, service definitions, environment/driver facts, benchmark JSON, thermal/error observations, backup and rollback instructions. Keep credentials in private local files, not the report.
12. Verify whether this specific deployment fits the applicable model and GeForce software terms. Record any unresolved licensing question rather than making a legal determination.
13. If multi-GPU WSL is persistently unreliable, capture a minimal reproduction and recommend a native-Linux validation path. Do not reinstall Windows, repartition disks, purchase infrastructure, change business data access, or migrate the host OS without the owner's explicit authorization.

Required outputs

- Read-only inventory report and an implementation decision log.
- Working authenticated local API with verified model/version pins.
- Validated launcher(s), startup units/tasks, health checks, and recovery notes.
- Comparison of applicable GPU layouts with measured latency, throughput, memory, and errors.
- A business-readiness checklist with each item marked passed, failed, pending, or not applicable.
- A deployment manifest with exact versions and model commits; no secrets.
- A final account of what runs now, how to start/stop/update/roll back, where evidence is stored, and anything that still needs owner or integrator action.

Use normal judgment for reversible work within the owner's authorization. Ask concise questions only for information, access, or approvals that materially block the next action. Do useful independent work while awaiting answers. Never label untested commands, unmeasured throughput, or an unverified reboot path as validated.

The important GPU limitation

The 4090 has no NVLink, and NVIDIA does not officially support direct CUDA peer-to-peer access between 4090 cards. Multi-GPU software can fall back to other paths, including host-staged transfers. Consequently, communication-heavy layouts can lose much of the benefit of extra GPUs. Linux does not remove the card's interconnect limitation. NVIDIA engineering clarification.

Several independent model instances can be a better fit for unrelated employee requests. Use measured demand to decide whether to replicate a smaller model or spread a larger model across more cards.

Have the integrator verify these before acceptance

  • DIMM placement: the CPU has 12 memory channels per socket. Ideally populate 12 approved ECC RDIMMs per CPU, following the motherboard's exact guide.
  • PCIe wiring: confirm electrical lane widths, any PCIe-switch uplinks, and CPU attachment for each GPU. Use suitable high-bandwidth connections; mining-style x1 risers are a poor fit.
  • Physical fit: eight large open-air GPUs need an appropriate chassis and airflow design. Fans, connectors, and sustained thermals need inspection under load.
  • NUMA: prefer groups local to one socket when feasible. GPU indices are not a topology map. WSL's virtual topology may not expose enough physical information; obtain the board's slot map.
  • Firmware: validate BIOS/chipset versions, AMD SVM/virtualization, Above 4G Decoding, and the vendor's eight-GPU settings. Do not indiscriminately disable IOMMU or security settings to chase performance.
  • Display use: if available, use BMC/integrated display capability so a serving GPU has fewer display allocations.
  • Network: ordinary text traffic is modest; bulk document ingestion and backups may justify 10 GbE. Choose from actual transfer requirements.

Power and thermal planning

Reference-specification GPUs account for 8 × 450 W = 3,600 W; the CPUs add 2 × 400 W = 800 W. The 4,400 W sum excludes RAM, disks, fans, and conversion losses. A 5–6 kW operating allowance corresponds to roughly 17,000–20,500 BTU/hour of heat. These are arithmetic planning estimates, not a measured wall load.

Have the integrator size the circuit, UPS, power distribution, redundant-PSU behavior, and cooling with headroom. A redundant PSU design must retain adequate capacity after the intended failure. If parts are still being selected, consider whether some CPU/RAM spending would be more useful as GPU memory, enterprise support, and a validated chassis.

Business deployment terms

NVIDIA's published GeForce software license restricts data-center deployment. Have the owner confirm the fit of the intended location and service model with the applicable terms; this runbook makes no legal determination. Also retain the chosen model's license and notices. GeForce software license.

05 / Plan for memory and demandChoose a model, then choose its layout

Dense model / precisionApproximate weight bytesInitial GPU allocation
8B / BF1616 GB1 card; convenient installation smoke test.
27B / BF1654 GB4 cards for a baseline with headroom.
32B / BF1664 GB4 cards, then test context/concurrency limits.
27B / INT413.5 GB theoretical packed minimum1–2 cards. The real checkpoint and runtime are larger.
70B / INT435 GB theoretical packed minimum2–4 cards; four is a conservative initial trial.
70B / BF16140 GB8 cards. Long contexts and high concurrency need careful capacity measurement.

Weight figures are decimal-byte estimates from parameter count × precision. Runtime tools often show GiB. Real models include other tensors, unquantized layers, metadata, workspaces, and model-specific buffers.

Memory budget

GPU memory = weights + KV cache + activations/temporary buffers + execution/communication overhead. Longer requests and more simultaneous requests consume additional capacity. System-RAM offload can help a model fit but adds transfers and may sharply reduce speed.

Initial model candidates

  • Installation check: Qwen/Qwen3-8B, a manageable model with documented vLLM support. Model card.
  • General business evaluation: Qwen/Qwen3.8-27B, first in BF16 and text-only mode. The official card documents vLLM and Apache 2.0 licensing. Official model card.
  • Memory/concurrency comparison: RedHatAI/Qwen3.8-27B-INT4, a documented W4A16 checkpoint. Check Ada-compatible kernels, measured quality, and memory use. INT4 model card.

These are evaluation candidates, not a promise of best quality. Use examples from the company's language, documents, coding tasks, and required output formats. Quantized weights must come from a compatible checkpoint or a validated conversion; a launch flag does not make an arbitrary model a sound INT4 deployment. Check the selected kernel's hardware support rather than copying a Blackwell-specific recipe.

Compare these allocations

LayoutReason to try itWhat to measure
2 × four-GPU BF16 replicasA clear quality baseline with independent request handling.PP4 versus TP4, latency, concurrency, host-transfer effects.
4 × two-GPU INT4 replicasMore independent capacity and VRAM margin per model.Quality change, per-request latency, collective overhead.
Up to 8 × one-GPU INT4 replicasEliminates inter-GPU communication within a request.Whether the actual model/runtime fits with useful context and buffers.
1 × larger eight-GPU modelWorthwhile if business quality materially improves.Communication cost, prompt processing, tail latency, memory.

Tensor parallelism divides operations within layers. Pipeline parallelism partitions layers. vLLM recommends considering pipeline parallelism on devices without NVLink to reduce communication overhead; model implementation support and workload determine the result. Use TP × PP equal to the GPUs assigned to the instance, with disjoint GPU groups between replicas. Parallelism guidance; model feature support.

Step 5 · GPU validation

Compute on every GPU independently

Verify computation on each detected GPU
UBUNTU • BASH / PYTHON
# If nvidia-smi is not on PATH, use:
# /usr/lib/wsl/lib/nvidia-smi -L
nvidia-smi -L

source "$HOME/llm/venv/bin/activate"

python - <<'PY'
import torch

assert torch.cuda.is_available(), "CUDA is unavailable"
count = torch.cuda.device_count()
print("Detected GPU count:", count)
assert count == 8, f"Expected 8 GPUs; detected {count}"

for i in range(count):
    a = torch.ones((1024, 1024), device=f"cuda:{i}")
    b = a @ a
    torch.cuda.synchronize(i)
    result = b[0, 0].item()
    assert result == 1024.0, (i, result)
    print(i, torch.cuda.get_device_name(i), "PASS", result)
PY

The test checks enumeration and a small calculation on each card. It is not a burn-in, communication benchmark, or guarantee of reliability under sustained load. Record the actual output; do not change an unexpected count to force the test to pass.

07 / Build the measured pilotPin the model and compare the layouts

Verify that the installed stable vLLM release supports the current model architecture, pipeline parallelism, and listed flags. Save the help output and consult its matching documentation. A model repository's commit pin controls weights/configuration; a separate dependency pin controls the runtime.

Download a fixed model revision

Resolve and download a reproducible business-model revision
UBUNTU • BASH / PYTHON

source venv/bin/activate

python - <<'PY'
from pathlib import Path

Create the reusable launcher

Save the following script at ~/llm/start-business.sh. Its defaults are a four-GPU BF16, text-only, 8,192-token pilot. It reads the private key and pinned model manifest. Environment variables allow controlled layout comparisons without editing the script.

Save as ~/llm/start-business.sh
UBUNTU FILE • BASH
#!/usr/bin/env bash
set -eo pipefail

LLM_ROOT="$HOME/llm"
cd "$LLM_ROOT"
source "$LLM_ROOT/venv/bin/activate"

set -a
source "$LLM_ROOT/vllm.env"
source "$LLM_ROOT/business-model.env"
set +a

test -n "$VLLM_API_KEY" || { echo "Missing VLLM_API_KEY" >&2; exit 1; }
test -n "$BUSINESS_MODEL_REVISION" || { echo "Missing model revision" >&2; exit 1; }

if [ -z "$LLM_GPU_IDS" ]; then LLM_GPU_IDS=0,1,2,3; fi
if [ -z "$LLM_PORT" ]; then LLM_PORT=8000; fi
if [ -z "$LLM_TP" ]; then LLM_TP=1; fi
if [ -z "$LLM_PP" ]; then LLM_PP=4; fi
if [ -z "$LLM_CONTEXT" ]; then LLM_CONTEXT=8192; fi
if [ -z "$LLM_MAX_SEQS" ]; then LLM_MAX_SEQS=8; fi

export HF_HOME="$LLM_ROOT/cache"
export CUDA_VISIBLE_DEVICES="$LLM_GPU_IDS"

exec "$LLM_ROOT/venv/bin/vllm" serve "$BUSINESS_MODEL" \
  --revision "$BUSINESS_MODEL_REVISION" \
  --served-model-name business-llm \
  --host 127.0.0.1 \
  --port "$LLM_PORT" \
  --dtype bfloat16 \
  --tensor-parallel-size "$LLM_TP" \
  --pipeline-parallel-size "$LLM_PP" \
  --distributed-executor-backend mp \
  --language-model-only \
  --reasoning-parser qwen3 \
  --max-model-len "$LLM_CONTEXT" \
  --max-num-seqs "$LLM_MAX_SEQS" \
  --gpu-memory-utilization 0.85

--max-model-len includes the request's prompt and generated tokens. --max-num-seqs is a scheduler limit, not a guarantee that all maximum-length requests fit or satisfy a latency target. The 0.85 GPU-memory fraction leaves initial headroom; actual allocations vary.

Model-specific serving settings: official vLLM recipe. Flag meanings: serving CLI.

Run competing layouts sequentially. A different port does not isolate GPU memory if two processes use the same cards. Replace the sample GPU groups with groups supported by the integrator's actual topology map; WSL may not expose that topology reliably.

08 / Make it usable for the businessAdd the application and identity layer

vLLM provides inference. Employees also need a chat/application interface, identity, policy, and document retrieval where required. Keep the pilot's inference ports on loopback and choose the access layer to fit the company's existing environment.

Recommended request path

Employee browser → HTTPS application / identity gateway → private vLLM replicas. A local document-retrieval service supplies authorized source passages when needed. The application handles conversation state, request limits, and user-visible citations.

  • HTTPS and identity: use company sign-in, role-based access, and managed certificates. Keep the backend key server-side rather than in a browser bundle.
  • Gateway controls: allow only intended routes, enforce user/rate/context/output limits, set suitable streaming/timeouts, and health-check individual replicas.
  • Load balancing: distribute requests between ports 8000 and 8001 once both are ready. Account for streaming connections and stateful application behavior.
  • Logging: choose retention and redaction intentionally. Prompt/response logs can contain confidential information; avoid collecting them by default without a business purpose.
  • Isolation: limit internal communication/administrative ports to trusted contexts. Keep raw vLLM off the public internet.

The vLLM API key is not a complete security perimeter. Upstream documents endpoints that are not protected by that key. The gateway should enforce authentication and route restrictions before traffic reaches the backend. vLLM security reference.

Start company-knowledge work with retrieval

  1. Extract text from approved documents and keep stable source IDs, versions, and permissions.
  2. Chunk/index the content using a local embedding model and retrieval store appropriate to its language and size.
  3. Retrieve relevant passages under the employee's actual permissions before sending them to the model.
  4. Generate answers with source references; support “insufficient evidence” responses and inspect grounding quality.
  5. Update or remove indexed content when the source changes, expires, or becomes inaccessible.

The CPU/RAM capacity is useful for this supporting work. Fine-tuning can later target specialized style or behavior after the baseline is evaluated. Full pretraining is a separate project and is outside this serving runbook.

If offline operation is required, pre-stage model snapshots, compatible packages, and required kernel artifacts, then test with egress disabled. Local hosting alone does not prove that the complete stack makes no outbound connections. Record telemetry choices and the verified offline behavior.

Configure the task for the Windows account that owns the distribution; using SYSTEM can select a different distribution registry context. Test the logged-out case, credentials, and local task policies rather than assuming a foreground terminal proves unattended operation.

Microsoft notes that systemd services alone do not keep the WSL instance alive. The long-running foreground process above is a session holder, not a health monitor for inference. Systemd restarts the model process; a separate readiness check should observe the API. Microsoft systemd lifecycle explanation.

Run the recovery exercise

  1. Close interactive Ubuntu sessions and confirm the API remains available through the intended application path.
  2. Reboot Windows during an agreed maintenance window. Do not log in interactively; verify the startup task, service, readiness, and authenticated inference.
  3. Exercise worker failure/restart on the dedicated pilot and verify automatic recovery plus actual model reload time.
  4. Exercise distribution restart and verify startup-task retry/monitoring behavior; record any manual action still needed.
  5. Check planned Windows-update/reboot behavior, task time limits, and post-update model readiness.

Automatic restart is not high availability. Both replicas still share one host, power, storage, and OS. Define the acceptable outage and use an additional recovery/failover arrangement when the business requires it.

Update and roll back deliberately

Keep the validated environment, model commit, and service configuration. Trial updates in a separate environment/configuration, rerun the relevant checks, and switch only after comparison. Rollback should restore the previous environment path, model pin, and launcher/service configuration. Protect the private key separately and document its rotation process.
